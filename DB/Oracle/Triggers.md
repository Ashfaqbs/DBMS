### 1. **What Are Triggers in SQL?**

A **trigger** in SQL is a special type of stored procedure that is automatically executed (or "triggered") when certain events occur in the database. Unlike functions and procedures, triggers are event-driven, meaning they execute in response to an action like `INSERT`, `UPDATE`, or `DELETE` on a table.

Triggers are mainly used for **enforcing business rules, maintaining audit trails, or updating dependent tables** automatically when certain actions occur.

---

### 2. **Trigger Basics and Types**

In Oracle SQL, triggers can be categorized based on when and how they are fired:
- **Before Triggers**: Fired before the triggering event (e.g., before an `INSERT`, `UPDATE`, or `DELETE`).
- **After Triggers**: Fired after the triggering event.
- **Instead Of Triggers**: Used with views, where you can't directly `INSERT`, `UPDATE`, or `DELETE` data.

Triggers are also classified by the event they respond to:
- **Row-level Triggers**: Fires for each row affected by the triggering event.
- **Statement-level Triggers**: Fires once for the entire triggering statement, regardless of how many rows are affected.

---

### 3. **Trigger Syntax**

Here’s the basic syntax for creating a trigger:

```sql
CREATE OR REPLACE TRIGGER trigger_name
BEFORE|AFTER INSERT|UPDATE|DELETE ON table_name
FOR EACH ROW -- For a row-level trigger; remove this line for a statement-level trigger
BEGIN
  -- Trigger logic goes here
END;
/
```

---

### 4. **Example 1: BEFORE INSERT Trigger**

Let’s start simple. Suppose you have an `employees` table, and you want to create a trigger that automatically sets the email to lowercase before inserting it into the table.

#### **Step 1: Create the Trigger**

```sql
CREATE OR REPLACE TRIGGER before_insert_employee_email
BEFORE INSERT ON employees
FOR EACH ROW
BEGIN
  :NEW.email := LOWER(:NEW.email); -- Ensure the email is in lowercase before inserting
END;
/
```

- **`:NEW`** refers to the new values being inserted into the table.
- **`:OLD`** (used in updates and deletes) refers to the old values before the change.
- This trigger ensures that whenever an employee is inserted, their email is automatically stored in lowercase.

#### **Step 2: Test the Trigger**

Now, try inserting a new employee with an uppercase email:

```sql
INSERT INTO employees (emp_id, first_name, last_name, email, hire_date)
VALUES (101, 'John', 'Doe', 'JOHN.DOE@EXAMPLE.COM', SYSDATE);

SELECT emp_id, first_name, last_name, email FROM employees WHERE emp_id = 101;
```

You will see that the email was automatically converted to lowercase.

---

### 5. **Example 2: AFTER INSERT Trigger for Audit Trail**

Let’s create a more advanced trigger that logs any new insertions into an `audit_log` table. This table will record details about any new employees added to the `employees` table.

#### **Step 1: Create an Audit Table**

First, create an audit table to store the log data:

```sql
CREATE TABLE employee_audit (
    audit_id NUMBER GENERATED BY DEFAULT AS IDENTITY,
    emp_id NUMBER,
    action VARCHAR2(50),
    action_time TIMESTAMP
);
```

#### **Step 2: Create the Trigger**

Next, create a trigger to log the insert actions:

```sql
CREATE OR REPLACE TRIGGER after_insert_employee_audit
AFTER INSERT ON employees
FOR EACH ROW
BEGIN
  INSERT INTO employee_audit (emp_id, action, action_time)
  VALUES (:NEW.emp_id, 'INSERT', SYSTIMESTAMP); -- Log the insert action
END;
/
```

This trigger fires after every `INSERT` on the `employees` table and records the action in the `employee_audit` table.

#### **Step 3: Test the Trigger**

Insert a new employee:

```sql
INSERT INTO employees (emp_id, first_name, last_name, email, hire_date)
VALUES (102, 'Alice', 'Smith', 'alice.smith@example.com', SYSDATE);

SELECT * FROM employee_audit;
```

You should see the audit log entry recording the `INSERT` action.

---

### 6. **Example 3: BEFORE UPDATE Trigger**

Let’s take this a step further by adding a **BEFORE UPDATE** trigger. Suppose you want to prevent employees from changing their hire date once it's set. You can use a trigger to enforce this rule.

#### **Step 1: Create the Trigger**

```sql
CREATE OR REPLACE TRIGGER before_update_hire_date
BEFORE UPDATE OF hire_date ON employees
FOR EACH ROW
BEGIN
  IF :OLD.hire_date IS NOT NULL THEN
    RAISE_APPLICATION_ERROR(-20001, 'Cannot change the hire date once it is set.');
  END IF;
END;
/
```

This trigger raises an error if someone tries to update the hire date.

#### **Step 2: Test the Trigger**

Now, try to update an employee’s hire date:

```sql
UPDATE employees SET hire_date = SYSDATE WHERE emp_id = 101;
```

You should get an error message: **`ORA-20001: Cannot change the hire date once it is set.`**

---

### 7. **Example 4: Row-Level vs Statement-Level Triggers**

#### **Row-Level Trigger**
This type of trigger fires for each row affected by the DML statement. You’ve already seen this in our previous examples (`FOR EACH ROW`).

#### **Statement-Level Trigger**
Let’s create a **statement-level trigger** that fires only once after an update statement is executed on the `employees` table, regardless of how many rows are affected.

#### **Step 1: Create the Trigger**

```sql
CREATE OR REPLACE TRIGGER after_update_employees_statement
AFTER UPDATE ON employees
BEGIN
  DBMS_OUTPUT.PUT_LINE('Employees table updated');
END;
/
```

This will print the message once, even if multiple rows are updated.

#### **Step 2: Test the Trigger**

Run an `UPDATE` query:

```sql
UPDATE employees SET email = LOWER(email);
```

In your output log, you will see: **`Employees table updated`**.

---

### 8. **Can We Use Triggers for Multiple Tables?**

Yes! Triggers can be created for multiple tables, but in Oracle, one trigger is tied to one table. However, if you want to perform actions across multiple tables, you can simply execute the logic inside the trigger.

For example, you can update or insert into another table from within the trigger for a different table.

---

### 9. **Modifying and Dropping Triggers**

- **Modify a trigger**: You can use `CREATE OR REPLACE TRIGGER` to modify an existing trigger.
- **Drop a trigger**: To remove a trigger, use:

```sql
DROP TRIGGER trigger_name;
```

---

### 10. **Things to Consider**

- **Performance**: Be cautious when using triggers. Since they automatically fire on certain events, they can sometimes introduce performance overhead if not used wisely.
- **Order of Execution**: If you have multiple triggers on the same table and event, the execution order is not guaranteed unless explicitly controlled.
- **Mutating Table Error**: In Oracle, you cannot directly query or modify the same table that fired the trigger. This can cause the **"mutating table"** error. To avoid this, you may need to handle the logic differently, perhaps with an `AFTER` trigger or using a package.
- **Testing**: It’s essential to test triggers thoroughly to avoid unexpected behaviors during database operations.

---

### 11. **Conclusion**

Triggers are powerful tools that allow you to automatically handle database events like `INSERT`, `UPDATE`, and `DELETE`. They help with enforcing business rules, maintaining audit trails, and automating repetitive tasks. However, they should be used with care to avoid performance issues or unintentional side effects.
